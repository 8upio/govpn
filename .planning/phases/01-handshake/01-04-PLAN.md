<objective>
Make the handshake hold up under the conditions it will actually meet, and convert the real
client's own traffic into permanent, fast-running proof of byte-exactness.

**User story (MVP):** **As a** govpn maintainer, **I want to** see the real OpenVPN 2.6
client complete its handshake over a 5-10% lossy, reordering link while the server presents a
multi-kilobyte certificate chain, and to have that session's own bytes committed as
regression vectors, **so that** the wire format and reliability behaviour stay verified
against the reference implementation on every commit without needing Docker.

Purpose: a reliability layer with guessed constants passes on a clean link and fails
unpredictably under loss — the loss gate is what distinguishes a working implementation from
one that merely appears to work. And golden vectors derived from a real client session are
the only vectors that can honestly be called reference-verified, which is exactly the
sequencing RESEARCH Open Question 1 recommends.

Output: bidirectional loss and reordering injection, a multi-kilobyte certificate profile,
committed real-client golden vectors asserted in the fast tier, and a CI pipeline running
both tiers.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Lossy, reordering link → the reliability layer | Adversarial-looking arrival patterns (drops, duplicates, reordering) reach the retransmit and window logic |
| Committed golden corpus → the repository | Key material and raw session bytes are persisted into a public repository |
| CI runner → Docker daemon and image registry | Automated builds pull and run the pinned client image without human review of each run |
