<objective>
Put a real, unmodified OpenVPN 2.6 client in front of the library and prove first contact:
the client's hard reset is authenticated and answered, and the client accepts that answer
and moves on to sending TLS control packets.

**User story (MVP):** **As a** govpn contributor, **I want to** run one command that stands
up a pinned real OpenVPN 2.6 client against a Go process embedding the library, **so that**
every byte-level claim from here on is verified against the reference implementation instead
of approximated from memory.

Purpose: interop testing, not code writing, is the real bottleneck for this project. The
harness built here is the gate every remaining plan in the phase — and every later phase —
is measured against. Standing it up on the reset exchange, before TLS exists, isolates
harness failures from protocol failures.

Output: `cmd/gentestpki`, a digest-pinned Debian OpenVPN client image, a two-service compose
topology, the harness server binary, a build-tagged Go driver, and a capture-based proof
that the control channel is tls-crypt wrapped on the wire.
</objective>

Write `cmd/gentestpki` as a single Go program using crypto/x509, crypto/rand, crypto/ecdsa
or crypto/rsa, and encoding/pem. It emits, into an output directory given by a flag
(default `test/interop/pki`, already gitignored): a self-signed CA; a server certificate
with ExtKeyUsageServerAuth signed by that CA; a client certificate with ExtKeyUsageClientAuth
signed by the same CA; a 256-byte tls-crypt static key wrapped in the OpenVPN Static key V1
envelope (the exact header and footer strings and hex body format read from crypto.c, with
512 hex characters); and the client `.conf` the container consumes. Namespace every subject
CommonName with a `govpn-interop-` prefix so this material can never be mistaken for
production credentials. Emit the tls-crypt key using crypto/rand, not by shelling out to the
openvpn binary — the whole harness stays self-contained in Go plus Docker.

The generated client .conf targets the server service by its compose network alias on UDP
port 1194 and declares: client mode, dev tun, proto udp, remote-cert-tls server, the inline
or file-referenced ca/cert/key, tls-crypt pointing at the generated key, `topology subnet`,
`cipher AES-256-GCM`, and `verb 4`. `topology subnet` and the explicit cipher belong in the
client config from the very first run so the config does not have to change when plan 01-03
and Phase 2 start relying on them.

Write `test/interop/Dockerfile` FROM `debian:bookworm-slim` referenced by sha256 digest, not

single apt layer with `--no-install-recommends`, then clean the apt lists. Record the exact
resolved `openvpn` package version in a comment so a future drift is visible in a diff.

Write `test/interop/server/main.go` as a real embedder of the library: it reads the generated
CA, server cert, server key, and tls-crypt key from the mounted PKI directory, builds a
tls.Config with ClientAuth set to require and verify the client certificate, ClientCAs set to
the generated CA pool, and MinVersion pinned to TLS 1.2 explicitly rather than relying on the
stdlib default floor; then it calls ovpn.NewServer and Serve on a UDP PacketConn bound to
0.0.0.0:1194. It writes one structured line per protocol event to stdout — at minimum, the
opcode and session ID of every accepted inbound control packet and every outbound one — and
exits 0 only after it has observed a valid hard-reset-client-v2 from a peer, answered it,
and then observed at least one subsequent opcode-4 control packet from that same peer
address and session ID. It exits non-zero on a deadline of 30 seconds with a message naming
what it last observed. That opcode-4 arrival is the assertion that matters: the real client
sends a control packet only after it has accepted the server's reset, so it proves first
contact independently of any log-string guess about the client's own output. Do not assert
on OpenVPN client log text in this task; RESEARCH Open Question 2 flags that the client may
reset and retry, and a log grep would be the vacuous assertion this plan prohibits.

Write `test/interop/docker-compose.yml` with two services on one user-defined bridge network.
The `server` service builds the repository, runs the harness server binary, is named
`govpn-interop-server`, runs as a non-root user (uid/gid 65534), declares no extra Linux
capabilities, no elevated-container flag, and no host device mapping. The `client` service
builds from `test/interop/Dockerfile`, mounts the generated PKI read-only, and does need
NET_ADMIN plus `/dev/net/tun` because the real OpenVPN client creates a kernel tun interface
— that asymmetry is the point, and it must be documented in a comment right there so nobody
later "simplifies" it by granting the server the same. Both services mount the PKI directory
produced by `cmd/gentestpki`.

After writing everything, run the harness and confirm the real client actually reaches

the server's structured lines and fix the protocol code or the config until it does.

Write `test/interop/pcap.go` as a minimal stdlib pcap reader — roughly the 24-byte global
header, then per-record a 16-byte header followed by the frame — that yields the UDP payload
bytes and direction for every record on port 1194. Handle the link types the `any` interface
produces (Linux cooked capture) as well as Ethernet, keying off the link type in the global
header rather than assuming one, and honour the byte-order magic. Return an explicit error on
an unknown link type instead of guessing an offset. This deliberately avoids adding a pcap
library: RESEARCH defers gopacket until Phase 2 or 3 needs programmatic pcap assertions, and
until then this reader keeps the dependency graph clean.

Write `test/interop/capture_test.go` behind the same `//go:build interop` tag. It loads the
capture from the passing harness run and the generated tls-crypt key, constructs one Wrapper
in the server key direction and one in the client direction, and for every captured payload
asserts: length is at least 49 bytes; the leading header byte's opcode is inside 3..11; and
the payload authenticates and decrypts under the wrapper matching its direction, with the
recovered plaintext parsing as a well-formed control packet. A single payload that fails to
authenticate fails the test, because that is exactly the case where a control packet went out
unwrapped. Assert additionally that the count of client-to-server control payloads is at
least two (the reset and one control packet), so the test cannot pass on an empty or
truncated capture — an assertion that measures nothing is the failure mode this plan
prohibits.

Do not assert on any fixed total packet count; loss and retransmission make counts vary
between runs, and a hardcoded count would be a fabricated baseline.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Docker Hub / Debian archive → interop client image | Third-party image layers and OS packages enter the test environment |
| Client container → server container over the bridge network | The real OpenVPN client's datagrams reach the library under test |

| Capture artifact → CI logs and developer machines | Raw wire bytes of a session are persisted to a file |
