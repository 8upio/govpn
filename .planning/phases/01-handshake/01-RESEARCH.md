# Phase 1: Handshake - Research

**Researched:** 2026-08-23
**Domain:** OpenVPN control-channel wire protocol, tls-crypt, control-channel reliability layer, `crypto/tls` over a custom `net.Conn`, Docker interop harness
**Confidence:** HIGH (wire format, tls-crypt, reliability layer — all read directly from the pinned C reference); MEDIUM (Go `net.Conn`/`crypto/tls` composition patterns, Docker/netem harness mechanics — standard, well-documented, but not phase-specific verified sources)

## Summary

Phase 1 has one job: get a real, unmodified OpenVPN 2.6 client through `HARD_RESET_V2` to a completed TLS handshake against a Go process, over tls-crypt, with mutual certificate auth — and prove it byte-exactly against the C reference, not from memory. Everything needed to do this was read directly from the pinned checkout at `/Users/svenloth/dev/openvpn-reference` (branch `release/2.6`, commit `c9b790f`): `ssl_pkt.c/h` (control-packet wire format and opcodes), `reliable.c/h` (the ACK/retransmission layer), `tls_crypt.c/h` (wrap/unwrap and the static-key file's slot convention), `packet_id.h` (the two *different* packet-ID types in play), `session_id.h` (8-byte session IDs), and `ssl.c` (the state machine and TLS-ciphertext fragmentation logic). Both open Research Flags from ROADMAP.md — the tls-crypt Ka/Ke slot convention and the control-packet fragmentation threshold — are resolved below with exact byte offsets and line citations.

The most important structural insight for the plan: **there are two unrelated "packet IDs" in a tls-crypt-wrapped control packet**, and confusing them is the single easiest way to build something that looks correct and silently isn't. The tls-crypt packet-id (8 bytes, long form: 4-byte sequence + 4-byte timestamp) lives in the clear, right after the session ID, and feeds the tls-crypt AEAD's synthetic-IV construction and its own independent replay window. The control-channel reliability-layer packet-id (4 bytes, short form) lives *inside* the tls-crypt-encrypted payload and is what the ACK/retransmission engine tracks. They are computed by different subsystems, incremented independently, and never compared to each other.

The second structural insight: Phase 1's target — "TLS established" — is the raw `crypto/tls` handshake completing (`Handshake()` returns nil, `ConnectionState().PeerCertificates[0]` has the verified CN). This is a strict subset of the C reference's `S_ACTIVE` state, which additionally requires the OpenVPN-level "Key Method 2" exchange (random material + options string) to happen *as TLS application data on top of* the completed handshake — that exchange is explicitly Phase 2 (`CTRL-04`, `WIRE-03`). The real client will attempt to send Key Method 2 data immediately after its own handshake completes; Phase 1's server only needs to not crash or reset the connection when that happens — it does not need to parse or respond to it yet.

**Primary recommendation:** Build the control-channel framing as a `net.Conn` implementation (opcode/session-id parsing, tls-crypt wrap/unwrap, and a hand-rolled reliability layer mirroring `reliable.c`'s state machine and constants exactly), then layer `crypto/tls` on top via `tls.Server(customConn, cfg)` unmodified. Verify tls-crypt and control-packet parse/serialize against isolated golden vectors generated by decrypting real captured traffic from the Docker-harnessed reference client — not hand-computed vectors, since no C toolchain is required to be part of this project's build.

### Pattern 1: Control-channel packet wire layout (tls-crypt mode)
**What:** The exact byte layout of every control packet sent or received once tls-crypt is active.
**When to use:** All opcodes when `TLS_WRAP_CRYPT` mode is active — this includes `P_CONTROL_HARD_RESET_CLIENT_V2` itself, not just post-reset traffic.
**Example:**
```
Source: openvpn-reference tls_crypt.h:48-95, ssl_pkt.c:120-165 (tls_wrap_control, TLS_WRAP_CRYPT branch)

On the wire (all fields except "encrypted payload" are sent as-is; the header is
authenticated but NOT encrypted):

byte 0        : opcode<<3 | key_id           (1 byte,  clear + authenticated)
bytes 1-8     : session_id                    (8 bytes, clear + authenticated)   [SID_SIZE]
bytes 9-16    : tls-crypt packet_id, long form (8 bytes, clear + authenticated)  [TLS_CRYPT_PID_SIZE]
                  = 4-byte sequence number (big-endian) || 4-byte unix timestamp (big-endian)
bytes 17-48   : HMAC-SHA256 auth tag          (32 bytes)                        [TLS_CRYPT_TAG_SIZE]
                  = top 256 bits of HMAC-SHA256(Ka, bytes[0:17] || plaintext)
                  the top 128 bits of THIS tag double as the AES-256-CTR IV
bytes 49+     : AES-256-CTR(Ke, IV=tag[0:16], plaintext)   [TLS_CRYPT_OFF_CT = 49]

Where "plaintext" (the tls-crypt src buffer, BEFORE encryption) is itself:

  [ack_count(1 byte)] [acked reliability packet-IDs, 4 bytes each, up to 8]
  [remote_session_id (8 bytes), ONLY if ack_count > 0]
  [this control packet's own reliability packet_id (4 bytes, short form — NOT
   the tls-crypt packet_id above; this is the DIFFERENT one the reliability
   layer tracks for ACK/retransmit]
  [TLS ciphertext fragment bytes, i.e. actual control-channel payload]

TLS_CRYPT_OFF_PID = 1 + SID_SIZE = 9
TLS_CRYPT_OFF_TAG = TLS_CRYPT_OFF_PID + TLS_CRYPT_PID_SIZE = 17
TLS_CRYPT_OFF_CT  = TLS_CRYPT_OFF_TAG + TLS_CRYPT_TAG_SIZE = 49
```

**What:** How to turn the 256-byte `--tls-crypt` key file into the four (Ka, Ke) values used for wrap/unwrap, from the server's point of view.
**When to use:** Key-file loading at server startup.
**Example:**
```

File format: PEM-style envelope, hex-encoded body, 256 raw bytes total.

  <512 hex chars = 256 bytes>
  -----END OpenVPN Static key V1-----

   "uint8_t *out = (uint8_t *) &key2->keys; const int keylen = sizeof(key2->keys);"]

Raw 256 bytes decode directly into `struct key2 { int n; struct key keys[2]; }`
where `struct key { cipher[64]; hmac[64]; }` [VERIFIED: crypto.h:149-155,171-185;
crypto_backend.h:188 MAX_CIPHER_KEY_LENGTH=64, crypto_backend.h:506 MAX_HMAC_KEY_LENGTH=64]:

  offset   0- 63 : keys[0].cipher   (first 32 bytes actually used — AES-256 key size)
  offset  64-127 : keys[0].hmac     (first 32 bytes actually used — SHA256 key size)
  offset 128-191 : keys[1].cipher
  offset 192-255 : keys[1].hmac
  [VERIFIED: crypto.c:824-866 init_key_ctx — cipher_ctx_init(ctx->cipher, key->cipher, ...)
   uses cipher_kt_key_size(kt->cipher) bytes; hmac_ctx_init(ctx->hmac, key->hmac, ...)
   uses the digest's own key size (32 for SHA256) — both slices are cipher_kt_key_size]

Slot assignment ("key direction"):
  tls_crypt_init_key(key, keydata, key_file, key_inline, tls_server) computes:
    key_direction = tls_server ? KEY_DIRECTION_NORMAL : KEY_DIRECTION_INVERSE
  [VERIFIED: tls_crypt.c:61-74]

  key_direction_state_init(): [VERIFIED: crypto.c:1505-1532]
    KEY_DIRECTION_NORMAL   → out_key=0 (encrypt), in_key=1 (decrypt)
    KEY_DIRECTION_INVERSE  → out_key=1 (encrypt), in_key=0 (decrypt)

  ⇒ SERVER (this project):  encrypt with keys[0] (Ka0=keys[0].hmac, Ke0=keys[0].cipher)
                             decrypt with keys[1] (Ka1=keys[1].hmac, Ke1=keys[1].cipher)
  ⇒ CLIENT (real openvpn):  encrypt with keys[1], decrypt with keys[0]

Note: unlike --tls-auth's optional `key-direction 0/1` config flag, --tls-crypt has NO
```

### Pattern 3: Reliability-layer constants and behavior (Research Flag, resolved)
**What:** Exact window sizes, retransmit timing, and fast-retransmit thresholds to mirror for interop-compatible behavior under the required 5–10% packet-loss test.
**When to use:** Sizing and timing the Go reliability-layer port.
**Example:**
```
Source: openvpn-reference ssl_pkt.h:70-71; reliable.h:44-56; reliable.c:664-699;
        ssl.c:1013-1023; options.c:876,880

RELIABLE_ACK_SIZE          = 8    max packet-IDs piggybacked per ACK record
RELIABLE_CAPACITY          = 12   max entries a reliable{} struct can hold
TLS_RELIABLE_N_SEND_BUFFERS = 6   send-side window (array_size passed to reliable_init)
TLS_RELIABLE_N_REC_BUFFERS  = 12  receive-side window
N_ACK_RETRANSMIT            = 3   fast-retransmit if this many LATER packets got ACKed
                                    (n_acks >= N_ACK_RETRANSMIT triggers early resend,
                                     independent of the timeout — reliable.c:674-685)

Retransmit timing:
  tls_timeout default        = 2 seconds  (options.c:876) — initial per-entry timeout
  Exponential backoff:        best->timeout *= 2  every time it's (re)sent (reliable.c:690)
  handshake_window default   = 60 seconds (options.c:880) — hard ceiling on total
                                handshake time before giving up (S_ERROR)

Packet-ID replay/ordering checks (reliable.c:44-95):
  reliable_pid_in_range1/2()  — wraparound-safe "is test within [base, base+extent)"
  reliable_not_replay()       — reject IDs at or below the lowest already-consumed ID,
                                 or matching any currently-active (not-yet-consumed) entry
  reliable_wont_break_sequentiality() — reject IDs that would need more buffer slots
                                 than RELIABLE_CAPACITY allows before the gap is filled

```

### Pattern 4: TLS ciphertext fragmentation across control packets
**What:** How a single TLS record from `crypto/tls`'s internal write gets split across multiple `P_CONTROL_V1` packets — the mechanism success criterion 4 (multi-KB cert chain) exercises.
**When to use:** Sizing the `net.Conn.Write()` implementation's outbound framing.
**Example:**
```
Source: openvpn-reference common.h:69,82; mtu.h:90; ssl.c:294-339,2811-2895; options.c:6608

TLS_CHANNEL_BUF_SIZE = 2048   hard ceiling on any single control-channel buffer
TLS_MTU_DEFAULT      = 1250   default --tls-mtu; clamped into [154, 2048]
                                (TLS_CHANNEL_MTU_MIN=154, TLS_CHANNEL_BUF_SIZE=2048)

Per-packet overhead subtracted before fragmenting (ssl.c:294-339,
calc_control_channel_frame_overhead — excluding the SOCKS-proxy-only +10 bytes,
which this project has no reason to replicate):
  tls-crypt overhead = tls_crypt_buf_overhead()
                      = packet_id_size(true) [8] + TLS_CRYPT_TAG_SIZE [32]
                        + TLS_CRYPT_BLOCK_SIZE [16]  = 56 bytes
  + opcode/length field allowance = 3 bytes
  + ACK_SIZE(RELIABLE_ACK_SIZE=8) = 1 + 8 + 4*8 = 41 bytes

  ⇒ with default tls-mtu=1250: usable control-payload-per-packet ≈ 1250 − 56 − 3 − 41
     ≈ 1150 bytes (reference subtracts 110 total incl. the SOCKS allowance this
     project can skip, landing closer to 1150-1190 usable bytes/packet)

Fragmentation loop (ssl.c:2866-2891): while the pending TLS-ciphertext buffer has
bytes left, grab a free reliability send-slot, copy up to max_pkt_len bytes into it,
mark it active-outgoing (opcode P_CONTROL_V1). Reassembly on the receive side is
implicit: the reliability layer delivers payload bytes to the TLS layer strictly in
packet-ID order, so concatenating in-order payloads IS TLS record reassembly — no
separate fragmentation header exists on the wire.

Recommendation for Go: don't exceed ~1200 bytes of control payload per outgoing UDP
datagram. The real client sizes its OWN outgoing buffers around the same 1250-byte
default; there's no protocol requirement to match exactly, but staying close avoids
surprising a client that assumes conservative peer behavior, and keeps every packet
safely under typical path MTU (1500) even after tls-crypt/IP/UDP overhead.
```

### Anti-Patterns to Avoid
- **Treating tls-crypt as a standard AEAD call:** It is a hand-assembled MAC-then-CTR-encrypt construction with the encryption IV *derived from* the MAC tag (synthetic IV). `cipher.NewGCM`/`AEAD.Seal` do not apply here at all — this is `crypto/hmac` + `crypto/aes`+`cipher.NewCTR`, wired together manually per Pattern 1 above.
- **Conflating the tls-crypt packet-ID with the reliability packet-ID:** They are different fields, different sizes (8 bytes long-form vs. 4 bytes short-form), computed by different subsystems (`tls_crypt_wrap`'s own `packet_id_send` vs. `reliable.c`'s `rel->packet_id`), and serve different purposes (AEAD/IV + tls-crypt-layer replay vs. ACK/retransmit ordering). See Pitfall 1.
- **Declaring "handshake complete" too early or too late:** Success is `tls.Conn.Handshake()` returning nil — not `S_ACTIVE` (which needs Key Method 2, Phase 2 scope) and not merely receiving the client's first `HARD_RESET_CLIENT_V2` packet.
- **Building the reliability layer's window/backoff constants from scratch/guessed:** Use the exact constants in Pattern 3 — the lossy-network success criterion (5–10% loss) is specifically testing whether these values (or close equivalents) hold up; guessed values may pass on a clean link and fail exactly at the loss-injection gate.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| TLS 1.2/1.3 handshake, record layer, cipher negotiation | A custom TLS state machine | `crypto/tls.Server(customConn, cfg)` | This is the entire point of the project's own "TLS from stdlib, not self-built" design decision — Go's TLS stack is exactly as capable as OpenVPN needs for the control channel, and reimplementing it would be enormous, security-critical, and pointless. |
| tls-crypt AEAD-like construction | A hand-rolled "good enough" authenticated encryption scheme | The exact MAC-then-CTR-with-tag-as-IV construction in Pattern 1, built from `crypto/hmac`+`crypto/aes`+`cipher.NewCTR` | Any deviation (different tag truncation, different AAD scope, different IV derivation) produces ciphertext a real OpenVPN client can never decrypt — an instant, silent interop failure indistinguishable from "encryption works but is wrong" until tested against the real client. |
| Reliability/retransmission logic | An ad-hoc retry-with-timeout loop | A `reliable.c`-equivalent state machine with the exact constants in Pattern 3 | Ad-hoc retry logic will pass a clean-link handshake test and then fail unpredictably under the mandated 5-10% loss/fragmentation test (success criterion 4) — the constants and fast-retransmit heuristic (`N_ACK_RETRANSMIT`) exist specifically to make lossy UDP links work for TLS. |
| Constant-time tag comparison | `bytes.Equal(tag, computed)` or `==` | `hmac.Equal(tag, computed)` | `crypto/hmac`'s own `Equal` function is constant-time by construction (wraps `subtle.ConstantTimeCompare`); a naive byte comparison introduces a timing side-channel on the tls-crypt integrity check, defeating one of tls-crypt's stated security goals. |

**Key insight:** Every "don't hand-roll" item above is a case where the correct behavior is either (a) already solved and audited in Go's stdlib (`crypto/tls`, `hmac.Equal`), or (b) fully specified by the C reference down to exact byte offsets and named constants (tls-crypt layout, reliability constants) — there is no reasonable "close enough" implementation for either category; both fail silently against the real client and only surface in the Docker interop harness.

## Common Pitfalls

### Pitfall 1: Confusing the two packet-ID types in a tls-crypt packet
**What goes wrong:** Using the reliability-layer's 4-byte control packet-ID as the tls-crypt AEAD packet-ID (or vice versa), or comparing them for replay detection against each other.
**Why it happens:** Both are called "packet ID" in casual reading of the protocol, both are `uint32`-based, and a naive read of `write_control_auth` (which touches both in sequence) makes it look like one flows into the other.
**How to avoid:** Keep them as genuinely separate types in the Go implementation (e.g. `type TLSCryptPacketID uint64` — encodes seq+timestamp — vs. `type ReliablePacketID uint32`), computed by genuinely separate subsystems: the `tlscrypt` package owns its own monotonic send counter and independent replay window; the `reliable` package owns its own. See Pattern 1 for exact byte offsets. `[VERIFIED: openvpn-reference packet_id.h:44,90-91 (packet_id_type = uint32, no timestamp by itself); tls_crypt.h:90 TLS_CRYPT_PID_SIZE = sizeof(packet_id_type)+sizeof(net_time_t) = 8 bytes long-form]`.
**Warning signs:** tls-crypt unwrap succeeds (HMAC verifies) but the reliability layer's ACK bookkeeping produces nonsense (duplicate/missing entries), or replay checks reject legitimate retransmissions.

### Pitfall 2: Getting the Ka/Ke slot direction backwards
**What goes wrong:** Server encrypts with the same slot the client also encrypts with (both use `keys[0]` or both use `keys[1]`), so neither side can decrypt the other's traffic — everything fails HMAC verification immediately.
**Why it happens:** The direction is implicit in a single boolean (`tls_server`) with no wire-visible marker; get the boolean backwards during key-file loading and both sides silently disagree.
**How to avoid:** Server always uses `KEY_DIRECTION_NORMAL` (`out_key=0, in_key=1`) per Pattern 2 — hardcode this, don't make it configurable, since `--tls-crypt` has no direction option in the C reference either.
**Warning signs:** Every incoming packet fails tls-crypt HMAC verification from the very first `HARD_RESET_CLIENT_V2` — if this happens, check slot direction before anything else.

### Pitfall 3: Wire-parsing untrusted UDP input without bounds checks
**What goes wrong:** A malformed or truncated UDP datagram (adversarial or just a corrupted packet) causes an out-of-bounds slice read/panic in the wire-parsing code.
**Why it happens:** The C reference uses manual length checks everywhere (`buf->len < (1 + SID_SIZE)` etc. — `ssl_pkt.c:313`) because C has no bounds-checked slices; it's tempting to assume Go's runtime panics are an acceptable substitute, but a panic in a UDP-packet-handling goroutine either crashes the process or (if recovered carelessly) leaves state inconsistent.
**How to avoid:** Every wire-parse function must explicitly check remaining buffer length before each field read and return a parse error (never let a slice index panic) — mirror the cheap-rejection-first structure of `tls_pre_decrypt_lite` (`ssl_pkt.c:305-423`): validate opcode/key-id/length before allocating any session state, so a spoofed-source flood of garbage UDP can't allocate unbounded memory.
**Warning signs:** Fuzzing or the lossy-network test producing truncated/reordered UDP payloads causes a panic instead of a clean parse-error return.

### Pitfall 4: Fragmenting outgoing TLS handshake data too aggressively or not at all
**What goes wrong:** Either (a) trying to send an entire multi-KB TLS record (e.g. server cert chain) in one UDP datagram, which risks IP fragmentation/drops and violates the real client's own expectations, or (b) fragmenting into tiny packets that blow through the 6-entry send window before the peer ACKs anything.
**Why it happens:** `crypto/tls`'s internal record writer doesn't know or care about the 1150-1200-byte-ish practical ceiling from Pattern 4 — that ceiling has to be enforced by the custom `net.Conn`'s `Write()`.
**How to avoid:** Chunk outgoing ciphertext into ≤~1200-byte control-packet payloads per Pattern 4, and ensure the reliability layer's `TLS_RELIABLE_N_SEND_BUFFERS`-equivalent window (6) is large enough to hold all fragments of one flight before requiring an ACK — a multi-KB cert chain will span multiple fragments and must all fit within (or be paced across) that window.
**Warning signs:** Success criterion 4's "realistic multi-KB certificate chain, fragmented across several control packets" test hangs or stalls specifically (not just "fails") — this is the fragmentation/windowing interaction, not tls-crypt or the base handshake.

### Pitfall 5: Declaring victory at the wrong protocol state
**What goes wrong:** Either closing/erroring the connection when the real client sends its Key Method 2 payload as TLS application data right after handshake completion (because Phase 1's server doesn't expect it), or trying to implement Key Method 2 parsing prematurely and scope-creeping into Phase 2.
**Why it happens:** `S_ACTIVE` in the C reference (`ssl_common.h:96-103`) genuinely does require Key Method 2 to have completed — a naive reading of "the handshake is done" from the C source's own state names could lead to over-scoping Phase 1.
**How to avoid:** Phase 1's definition of done is `tls.Conn.Handshake()` returning nil plus a verified peer cert CN — full stop. The `net.Conn`/`Session` plumbing should tolerate (buffer or silently discard) any TLS application data that arrives after that point without erroring, since Phase 2 will be the one to actually read and act on it.
**Warning signs:** Test harness assertions checking for OpenVPN client log lines like "Initialization Sequence Completed" (which require full Phase 2 completion) instead of the client's own TLS-handshake-complete log line.

## Code Examples

### tls-crypt wrap (Go, from Pattern 1/2)
```go
// Source: derived from openvpn-reference tls_crypt.c:145-220 (tls_crypt_wrap),
// tls_crypt.h:89-95 (offsets/sizes). NOT copied C — a from-scratch Go port of the
// documented algorithm, to be verified against golden vectors before trusting it.

const (
    tagSize   = 32 // TLS_CRYPT_TAG_SIZE = 256/8
    blockSize = 16 // TLS_CRYPT_BLOCK_SIZE = 128/8 (also the AES-CTR IV size)
)

// header = opcode<<3|keyID (1 byte) || session_id (8 bytes)
// pid    = 4-byte seq || 4-byte unix timestamp, big-endian (tls-crypt's OWN counter)
func wrap(ka, ke []byte, header []byte, pid [8]byte, plaintext []byte) ([]byte, error) {
    aad := append(append([]byte{}, header...), pid[:]...) // 9 + 8 = 17 bytes

    mac := hmac.New(sha256.New, ka)
    mac.Write(aad)
    mac.Write(plaintext)
    tag := mac.Sum(nil) // 32 bytes; top 16 bytes double as the CTR IV

    block, err := aes.NewCipher(ke) // ke must be exactly 32 bytes (AES-256)
    if err != nil {
        return nil, err
    }
    stream := cipher.NewCTR(block, tag[:blockSize])
    ciphertext := make([]byte, len(plaintext))
    stream.XORKeyStream(ciphertext, plaintext)

    out := append(append([]byte{}, aad...), tag...)
    return append(out, ciphertext...), nil
}
```

## Open Questions

1. **How should the plan sequence golden-vector testing against the "isolated vectors" requirement (success criterion 3) given the harness-based vector-generation approach (A4)?**
   - What we know: WIRE-01/WIRE-04 require golden-vector tests verified against the C reference; the most reliable way to generate correct vectors without a C toolchain dependency is to capture and decrypt real traffic from the Docker-harnessed client.
   - What's unclear: Whether the plan should build a minimal wire/tls-crypt implementation first (tested only against hand-reasoned/self-consistent vectors), get the Docker harness working second, then backfill "real" golden vectors from a captured session as a later task — or invert the order.
   - Recommendation: Sequence as (1) wire+tls-crypt implementation with self-consistency tests (wrap→unwrap round-trips on synthetic data) to unblock development, (2) Docker harness stood up in parallel against a stub/no-op TLS conn to validate transport-only plumbing, (3) real end-to-end run once both are ready, capturing the golden vectors as a byproduct that then get committed to `testdata/golden/` and asserted against in a fast (`go test ./...`-tier) test going forward.

2. **Does the real OpenVPN 2.6 client tolerate a server that goes silent after `Handshake()` completes (Phase 1's intentional stopping point), or will it treat this as a failure and disconnect/retry?**
   - What we know: The client will send Key Method 2 data as TLS application data immediately after its own handshake completes; Phase 1's server has no obligation to read or respond to it.
   - What's unclear: Whether the client has a timeout waiting for a Key Method 2 response that would cause it to tear down the connection (and re-send `HARD_RESET_CLIENT_V2`) before the interop harness can assert "TLS established" was reached — this affects how the harness detects success (must capture the moment of completion, possibly via client-side log line, not wait for full "Initialization Sequence Completed").
   - Recommendation: During interop-harness implementation, capture and grep the client's own verbose (`--verb 4`+) log output for its TLS-handshake-complete line (something like `Peer Connection Initiated`/`VERIFY OK`/cipher confirmation) as the success signal, rather than relying on a later log line. If the client resets and retries, that's still a valid transient state to observe from — the harness just needs to catch the first successful handshake, and the reliability layer's own resend-tolerant design already means repeated `HARD_RESET_CLIENT_V2` attempts should be handled gracefully.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|----------------|---------|---------------------|
| V2 Authentication | yes | Mutual cert-based TLS via `crypto/tls` (`ClientAuth = RequireAndVerifyClientCert`, `ClientCAs` pool) — never `InsecureSkipVerify`, never a custom cert-chain walker |
| V3 Session Management | yes (adapted) | 8-byte session IDs generated via `crypto/rand`, not `math/rand`; session dispatch keyed by (remote UDP addr, session ID) with the cheap-rejection triage of Pitfall 3 before any state allocation |
| V4 Access Control | no | Not applicable at the protocol-handshake layer; no authorization decisions happen in Phase 1 |
| V5 Input Validation | yes | Every wire-parse function must explicit-bounds-check before reading fields from untrusted UDP input (Pitfall 3); tls-crypt HMAC must be verified (fail closed) before any content derived from the packet is trusted or parsed further |
| V6 Cryptography | yes | Never hand-roll AES-CTR/HMAC-SHA256; use `crypto/aes`+`crypto/cipher`+`crypto/hmac`+`crypto/sha256` exclusively per Pattern 1; constant-time tag comparison via `hmac.Equal` (Don't Hand-Roll table) |

### Known Threat Patterns for OpenVPN control-channel handling

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|------------------------|
| Spoofed-source `HARD_RESET_CLIENT_V2` flood (session-allocation DoS) | Denial of Service | Cheap opcode/key-id/length triage before allocating any per-session state, mirroring `tls_pre_decrypt_lite` (`ssl_pkt.c:305-423`) — reject before allocate. Full HMAC-based session-id hardening (`calculate_session_id_hmac`, `ssl_pkt.c:485-525`) is available in the reference as a stronger defense but is explicitly optional for Phase 1's MVP scope — flag as a follow-up hardening item, not a Phase 1 blocker |
| tls-crypt tag forgery / bit-flipping | Tampering | HMAC-SHA256 verified via `hmac.Equal` (constant-time) before any decrypted content is trusted; reject and drop on mismatch, no partial-trust fallback |
| Replayed captured control packets | Tampering / Information Disclosure | Independent replay windows in both the tls-crypt layer (its own packet-ID) and the reliability layer (its own packet-ID) — see Pitfall 1; reject IDs at/below the lowest already-consumed value per `reliable_not_replay` semantics (`reliable.c:487-512`) |
| Certificate validation bypass (wrong/self-signed cert accepted) | Spoofing | `Config.ClientCAs` pinned to the project's own CA pool, `Config.ClientAuth = RequireAndVerifyClientCert`, `Config.MinVersion = tls.VersionTLS12` — all explicit, none left at Go's shifting defaults |
| Unbounded memory growth from malformed/oversized packets | Denial of Service | Bounds-check every buffer read (Pitfall 3); cap per-packet payload size consistent with `TLS_CHANNEL_BUF_SIZE` (2048) as an upper sanity bound even before tls-crypt/wire parsing begins |
