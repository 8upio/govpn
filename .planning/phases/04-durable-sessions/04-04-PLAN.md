<objective>
Prove that dead sessions do not accumulate. One long-lived server process takes 20 connect,
use, and clean-disconnect cycles from a real OpenVPN 2.6 client, and finishes with its goroutine
count and post-GC heap back at the baseline it measured after the first cycle.

Phase goal (ROADMAP, verbatim): *A connected client stays usable for hours and leaves cleanly —
key renegotiation does not break traffic, and dead sessions do not accumulate.*

Purpose: ROADMAP success criterion 3 for this phase, and the empirical backstop behind the fast-tier
goroutine sentinel plan `04-02` added.
Output: a tagged, longer-timeout soak target that a CI job or a developer runs deliberately.
</objective>

  <action>
Add the measurement, choose the tolerances from observed data, and give the soak its own target.

**Sampling.** In soak mode, sample twice: a baseline immediately after the FIRST cycle's session is
observed closed, and a final sample after the LAST cycle's. Never sample at process start — a
cold-start baseline hides the first session's own lazily-initialized runtime state (listeners,
buffers, pools) and would make ordinary warm-up look like a leak. Each sample is
`runtime.NumGoroutine()` plus `runtime.ReadMemStats`' `HeapAlloc` taken after forcing collection;
call `runtime.GC()` twice before reading, so objects that only become unreachable during the first
collection's finalization are also accounted for. Give both samples a brief settle delay before
being taken, so a goroutine that is exiting but has not yet been descheduled is not miscounted, and
document that delay's purpose in its own constant. Emit
`soak_goroutines_baseline=`, `soak_goroutines_final=`, `soak_heap_baseline=`, `soak_heap_final=` on
the PASS line.

**Tolerances.** Scale the scenario to 20 cycles. Run it, read the real numbers, then choose a
goroutine tolerance and a heap tolerance and write both as named constants in `interop_test.go`
whose doc comments state the observed values they were chosen against and why the margin is what it
is. The goroutine tolerance should be tight — a per-session leak shows up as roughly one extra
goroutine per cycle, so anything near 20 must fail — while the heap tolerance absorbs Go's allocator
behavior without absorbing 20 sessions' worth of retained state. Assert both, plus
`soak_cycles_observed` equal to the configured count, plus every cycle's probe `result=ok`.

**Pool reuse.** Assert that the tunnel IPs the server assigned across the 20 cycles came from the
same small address range rather than climbing — evidence that `Close` released each IP and peer-id
back to the pool (WR-04's ordering, `session.go:491-511`). Log the assigned IP per cycle in the
server's per-cycle line so the assertion has something to parse.

**Its own target.** Add a `soak` target to the `Makefile` that regenerates the PKI and runs only the
soak test with its own long timeout, with a comment stating it is deliberately not part of `test` or
`interop` because it takes minutes. Leave `.DEFAULT_GOAL` and the `test`/`gates`/`interop` targets
untouched.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Repeated client sessions → one long-lived server process | 20 cycles is the adversarial case for per-session state: anything retained per session accumulates 20-fold and becomes visible. |
| Harness assertions → CI signal | A soak assertion that cannot fail is worse than none, because it certifies the property it does not check. |
| Docker network → server container | The server's unprivileged posture is re-asserted on the soak scenario like every other. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-15 | Denial of Service | per-session goroutine leak exhausting a long-running embedder | high | mitigate | Task 2's goroutine flatness assertion, tuned tight enough that one leaked goroutine per cycle fails it, and Task 3's demonstration that it does. |
| T-04-16 | Denial of Service | per-session heap retention (sessions, wrappers, lame-duck slots) never released | high | mitigate | Task 2's post-GC HeapAlloc flatness assertion, demonstrated failing in Task 3 by deliberately retaining closed sessions. |
| T-04-17 | Denial of Service | tunnel-IP / peer-id pool exhaustion across many sessions | medium | mitigate | Task 2's pool-reuse assertion: 20 cycles must be served from the same small address range, which only holds if `Close` released each allocation exactly once (WR-04 ordering). |
| T-04-18 | Spoofing (of test evidence) | a soak that passes without observing the cycles, or with a cold-start baseline | high | mitigate | Task 3's `TestPhase4SoakAssertsObservedCycleCount` and `TestPhase4SoakSamplesBaselineAfterFirstCycle` gates. |
| T-04-19 | Denial of Service | the soak slowing every developer's default test loop until it is disabled | low | mitigate | Its own `make soak` target with its own timeout, plus the `TestPhase4SoakIsNotInDefaultTargets` gate. |
