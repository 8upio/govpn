Purpose: RESEARCH.md read `net/http`'s own source this phase and found three things a
hand-rolled `net.Conn` typically gets wrong, two of which break page loads in ways that
only show up as a hung `curl` in a Docker run. This plan turns each of those three findings

## The three `net/http` findings this plan implements

Each was verified by RESEARCH.md against the local Go 1.26.1 toolchain source, with file
and line references, not from memory.

1. **Deadlines are load-bearing (Pitfall 1).** `(*http.conn).readRequest` calls
   `c.rwc.SetReadDeadline(hdrDeadline)` unconditionally (`net/http/server.go:992`). If a
   `Read` blocked past that deadline returns a plain error, `net/http` cannot tell "idle
   keep-alive client" from "broken connection". The error must satisfy `net.Error` with
   `Timeout() == true` and wrap `os.ErrDeadlineExceeded` (`net/net.go:158-159`).
2. **`SetKeepAlive` is not needed (Pitfall 2).** `http.Serve` and `(*Server).Serve` take a
   caller-supplied listener as-is and never wrap it; the keep-alive wrapper lives only
   inside `ListenAndServe`'s own `net.Listen` path (`net/http/server.go:2940-2943`,
   `3348-3361`). Implementing it would be dead code on this call path — this plan's
   prohibition list makes that a decision rather than an omission.
3. **`CloseWrite` is found structurally (Pitfall 3).** `(*conn).closeWriteAndWait` checks
   whether the underlying conn satisfies an unexported `closeWriter` interface
   (`CloseWrite() error`) and calls it before waiting briefly and fully closing
   (`net/http/server.go:1772-1787`). Without it, `net/http` silently falls back to a full
   close, and a browser can perceive the last keep-alive response as a broken connection.

  <action>
Harden the deadline path against the specific sequences `net/http` produces, since those
are the only ones that matter for this phase's actual call path.

The load-bearing behavior is **clearability**: `readRequest` sets a header deadline, and on
a successful read the server clears or replaces it before the handler runs. A conn that
treats deadline expiry as terminal — resetting, closing, or entering an error state it
cannot leave — turns every idle keep-alive connection into a broken one, which is exactly
RESEARCH.md Pitfall 1's warning sign. Implement expiry as a *per-call* outcome: the blocked
`Read`/`Write` returns the timeout sentinel, connection state is untouched, no segment is
emitted, and the next call after the deadline is cleared or extended proceeds normally. Add
a comment saying so, because "return an error but change nothing" is a discipline that
looks like an omission to a later reader.

`Write` returning a timeout must report the byte count actually accepted into the send
buffer. `io.Writer`'s contract is that `n < len(p)` accompanies a non-nil error;
overstating `n` would make a caller believe bytes were sent that were not, and `net/http`
writes response bodies through exactly this path.

Guard deadline fields with the connection's existing mutex and never hold it across a
blocking select. `TestTCPDeadlineFromAnotherGoroutine` is what proves the standard
supervisor-sets-a-deadline-on-a-blocked-reader pattern is race-free.

`TestTCPDeadlineUsesWallClockNotProtocolClock` is this plan's structural guard: it fails if
someone later "unifies" the two timing sources for tidiness. Write the test so its failure
message names the reason (a deadline is the caller's contract with `net/http`; the protocol
`Clock` exists so plan 03-03's retransmit tests need not sleep), not merely the expected
value.

Finally, add `TestHTTPIdleKeepAliveDoesNotReset` as the integration-shaped check on the
whole path: a real `http.Server` with a short `ReadHeaderTimeout` and a client that connects
and stays silent. The server should close that connection on its own timeout without
disturbing the listener, and a subsequent client should be served normally — this is the
scenario that, if broken, produces the intermittent hung-`curl` symptom in plan 03-06's
Docker run rather than a clean fast-tier failure here.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Authenticated tunnel peer → accepted `net.Conn` | The peer controls the timing and shape of every byte `http.Server` reads, including sending nothing at all |
| `net.Conn` → `http.Server` | The stdlib server makes assumptions about deadline and close semantics; violating them changes its behavior in ways the netstack cannot see |
| `http.Handler` → `Write` on the conn | Handler-produced bytes cross back through the TCP send path, possibly from a goroutine the stack did not create |
