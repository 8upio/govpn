<objective>
Make a live session survive key renegotiation. A real client's `P_CONTROL_SOFT_RESET_V1` — and,
independently, the server's own `reneg-sec` deadline — starts a full new TLS handshake plus Key
Method 2 exchange under an incremented key-id on the *same* `tls_session`: same 8-byte session
IDs, same tls-crypt `Wrapper`, same tunnel IP and peer-id. The old data key stays decryptable for
a bounded transition window while transmit switches to the new one.

Phase goal (ROADMAP, verbatim): *A connected client stays usable for hours and leaves cleanly —
key renegotiation does not break traffic, and dead sessions do not accumulate.*

Purpose: SESS-04. Everything downstream in this phase — the shortened-reneg interop scenario, the
soak run — needs a working rollover to exercise.
Output: two-slot key state on `Session`, a renegotiation driver, a key-id-aware control-packet
router, `Config.RenegSec`, and fast-tier clock-injected proof that traffic survives the rollover.
</objective>

Decisions this plan implements (from `04-CONTEXT.md`; IDs assigned this phase, continuing the
project's own D-NN series, which ended at D-16 in Phase 2):

- **D-17** — Bidirectional: handle client-initiated SOFT_RESET fully AND run the server's own
  `reneg-sec` timer (both sides run timers, first to fire wins — reference behavior).
- **D-18** — Lame-duck key transition per the C reference: new key under an incremented key-id
  (mod 8, skipping 0), old key valid for the transition window, decrypt accepts both during the
  overlap, transmit switches once the new key is live; the embedder's `Session` stays open with
  zero packet-visible interruption.
- **D-19** — `Config.RenegSec time.Duration` (0 = default 3600s). `reneg-sec` is NOT a pushed
  option.
- **D-20** — Renegotiation = full new TLS handshake + Key Method 2 over the same control channel
  under the new key-id, reusing Phase 1 control-channel machinery and Phase 2 key derivation
  per-key.
- **D-25** — Assumption delta (see `COVERAGE.md`): the fixed `dataChannelKeyID = 0` constant
  retires; the per-session data key becomes a key-slot structure.

Claude's discretion, exercised here: the key-slot state is two named fields (`primary`,
`lameDuck`), not a `map[uint8]`, per RESEARCH's "Alternatives Considered" — the reference itself
only ever holds two live slots (`KS_SIZE = 2`, `ssl_common.h:448-451`).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet → `Server.Serve` UDP read loop | Any host can send arbitrary datagrams to the tunnel port; nothing is trusted before tls-crypt `Unwrap` succeeds. |
| tls-crypt-authenticated control channel → renegotiation state machine | A packet that passes tls-crypt is authentic to the shared group key but its *contents* (opcode, key-id) are still peer-supplied and must be validated locally. |
| Renegotiated TLS session → data-channel key slots | New key material only becomes the transmit key after mutual cert auth and Key Method 2 complete; the old key's validity is bounded by the transition window. |
