<objective>
Turn first contact into a completed TLS handshake. Build the reliability layer and the
control-channel `net.Conn` the phase's whole architecture rests on, put stdlib `crypto/tls`
on top unmodified, and prove a real OpenVPN 2.6 client reaches "TLS established" with mutual
certificate authentication.

**User story (MVP):** **As a** Go developer embedding govpn, **I want to** have a real
OpenVPN 2.6 client authenticate to my server with its certificate and complete the TLS
handshake, **so that** I can identify the connected peer by its verified CommonName and the
control channel is ready to carry Key Method 2 in the next phase.

Purpose: this is the phase goal. It is also the point where the architecture's central bet —
that OpenVPN's control-channel framing can be expressed as a `net.Conn` so Go's audited TLS
stack works unchanged — either holds or does not.

Output: `internal/reliable`, `internal/ctrlconn`, the `ovpn.Session` type, `OnSession`
firing, and an interop run in which the real client and the library both report the peer's
verified certificate CN.

  <behavior>
    - Retransmit: a packet sent and left unacknowledged is resent after 2 seconds, then 4, then 8 — the per-entry timeout doubles on every send
    - Fast retransmit: once 3 later packets have been acknowledged, the still-unacknowledged earlier packet is resent immediately, independent of its timeout
    - Send window: with 6 slots occupied and none acknowledged, a seventh Write blocks or is deferred rather than overwriting an unacknowledged entry
    - Receive window: 12 slots; an ID that would need more slots than capacity before its gap can be filled is refused rather than buffered
    - Replay: an ID at or below the lowest already-consumed ID is rejected; an ID matching a currently-active un-consumed entry is rejected; a legitimate retransmission of an un-consumed ID is accepted once
    - Ordering: IDs delivered 3, 1, 2 are consumed as 1, 2, 3, and 1 is never delivered after 2
    - Wraparound: the range checks behave correctly across the 32-bit packet-ID wrap boundary
    - ACK policy: an outgoing packet piggybacks up to 8 pending ACKs plus the peer session ID; with more than 8 pending, the remainder stay queued for the next packet; with ACKs pending and nothing else queued, an ACK-only packet is emitted
    - Handshake window: a session with no completed handshake after 60 seconds is torn down and its buffers released
  </behavior>
  <action>

tests for each. Drive time from an injectable clock rather than wall-clock sleeps so the

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Authenticated control payload → `internal/reliable` | Attacker-chosen (but tls-crypt-authenticated) packet IDs and ACK arrays drive buffer allocation |
| `internal/ctrlconn` byte stream → `crypto/tls` record layer | Reassembled attacker-influenced bytes enter the TLS state machine |
| `crypto/tls` peer certificate → `ovpn.Session.PeerCN` | Peer identity crosses into the embedder's callback |
| Half-open session state → server memory | Pre-handshake sessions hold buffers before any peer identity is established |
